# Project storage and local recovery

Implemented first storage slice, 2026-09-22. This is partial delivery of roadmap T02/T03, not completion of F01/F14 or the full implementation goal.

## Portable `.luma` container v3

The browser now retains original compressed image bytes as `Blob` objects rather than eager base64 strings. New downloads have MIME `application/x-luma` and keep the `.luma` extension. The inner document schema is version 16: RLE pixel selection coverage and raster erasure records (v15 added HSL adjustments) (v14 added layer comps, v13 linked local-image snapshots, v12 smart-filter masks, v11 ordered smart filters, v10 embedded components, v9 retouch patches, v8 tonal strokes, v7 guides, v6 layer affine bases, v5 affine selections, v4 adjustment layers, v3 masks and v2 authored metadata). Valid inner v1–v15 documents migrate to v16 when opened. Older readers reject unsupported schemas rather than discard their new fields. The outer container remains version 3. The loader still accepts legacy version-1 JSON/base64 project files and converts their assets to blobs without altering their bytes. The reader accepts v1 JSON and v2 binary input; new saves write v3. Older builds cannot open v3 downloads.

The binary layout is:

| Segment         | Representation                                                                                         |
| --------------- | ------------------------------------------------------------------------------------------------------ |
| Signature       | Eight bytes: `4c 55 4d 41 33 0d 0a 00` (`LUMA3`, CR, LF, NUL)                                          |
| Manifest length | Eight-byte unsigned little-endian integer; must fit safe JavaScript offsets and the actual file bounds |
| Manifest digest | 32 raw SHA-256 bytes covering the exact UTF-8 manifest bytes                                           |
| Manifest        | UTF-8 JSON `{ format: "luma", version: 3, document, assets }`                                          |
| Asset payload   | Consecutive original compressed image blobs, in manifest order                                         |

Each asset entry has `id`, `name`, `width`, `height`, `type`, `offset`, `size` and lowercase hexadecimal `sha256`. Offset is relative to the start of the asset payload. Width/height describe the browser-decoded orientation used by the document. Payload offsets must be contiguous and non-overlapping; IDs must be unique; referenced assets must exist. Only PNG/JPEG/WebP assets are currently supported. Truncation, invalid ranges, missing references and trailing bytes fail before replacement of the current document. Decoded dimensions are checked against the manifest during load.

`serializeProject` and host `editor.saveProject()` return `Promise<Blob>`. They capture the document and immutable source blobs before yielding, then hash sources sequentially. The result is a Blob composed from header, manifest and original blobs. `readProject` verifies the manifest digest before parsing it, validates structure, then verifies each asset checksum before returning. It reads the header/manifest into memory and slices asset blobs; hashing currently materializes one compressed asset at a time. `loadProject` validates and decodes assets in a staging store; failures dispose that store. Opening a project checks that the active document/revision has not changed before replacing it. Serialization includes assets referenced by current layers and clone tiles, not transient caches or undo history.

This eliminates source-sized base64 conversion and concatenation on the new save/load path. It is not region decoding or fully disk-backed rendering: original image bitmaps remain decoded in memory, the document manifest is materialized as JSON, and legacy input still materializes its JSON/base64. V3 integrity checks cover manifest and source bytes in addition to structural and decoder checks. Checksums detect corruption, not malicious replacement by someone who can recompute hashes. V1/v2 inputs retain structural/decoder checks without invented integrity guarantees. A standards-based archival interchange format remains a future decision. No new image or project megapixel/byte cutoff was added.

## Local recovery checkpoints

Committed document changes schedule a checkpoint after approximately 600 ms; continuing edits coalesce into the latest pending snapshot. Temporary brush previews are not serialized. Selection-only state changes do not need a new checkpoint. Status is acknowledged only after an IndexedDB transaction commits.

The version-2 `luma-recovery` database has `checkpoints` and `assets` object stores. Existing version-1 records remain readable; older builds cannot write to the upgraded database. Each editing session gets a random recovery ID. A checkpoint atomically writes its document manifest and missing source blobs, retains the preceding two checkpoints, and deletes blobs no longer referenced by any of the three retained revisions. Existing immutable blobs are reused on later revisions. New records include SHA-256 checksums for the document/asset-key manifest and source blob bytes plus asset metadata. Hashing completes before the IndexedDB transaction; compressed source blobs are hashed sequentially, temporarily materializing one blob at a time. This is integrity detection, not authentication against malicious code. Independent tabs and opened documents have independent IDs; they cannot silently overwrite each other's checkpoints. A failed transaction leaves the preceding checkpoint and asset set intact.

**Recover work** in the tool rail lists completed checkpoints. Restoring validates checkpoints newest-first and opens the newest intact revision as a separate editable copy; it does not delete the checkpoint. If newer revisions are damaged, the dialog reports the skipped count and restored time and warns that newer edits may be missing. If all retained revisions fail, current work is unchanged. Legacy records have structural validation but no retroactive checksum guarantee. Current work is flushed first. If that flush fails, the panel requires downloading the current project before restoring. Old checkpoints can be removed with a second confirmation action; the active session's checkpoint cannot be removed from that dialog. There is no automatic age-based deletion yet.

The footer distinguishes pending, saving, saved and failed recovery. Storage failure does not disable editing or external project downloads. Local recovery is not a backup: clearing site data, private-mode behavior, quota limits, storage eviction, disk failure and power loss can remove it. A strict IndexedDB durability hint is requested for checkpoints, but it is not a universal guarantee against OS/storage failure. Work newer than the last acknowledged checkpoint may be lost on termination. Per-document recovery reopens the latest document state without an undo stack; workspace checkpoints additionally retain the history window described below.

Remaining T02/T03 work: longer-lived history policy, broader quota-failure testing and reclamation policy, source-content deduplication, disk-backed/lazy decoding, recovery discovery notifications and broader browser/crash testing. T01 still needs a dedicated benchmark corpus/harness; the existing 50 MP workflow is a regression baseline, not a complete performance program.

## Verification

`tests/project.test.ts` checks blob byte preservation, legacy reading, truncation, offsets, duplicates, missing references and trailing data. `tests/recovery.e2e.ts` exercises real IndexedDB reload recovery, an aborted checkpoint transaction, independent tabs and unavailable storage. Existing editor/tool tests cover original resolution, clone assets, masks/styles and source-resolution PNG output across project round trips. Record actual executed results in the implementation roadmap.

Document schema v3 also accepts `mask.kind: "vector"` with compound closed Bézier geometry. The outer container remains v2. Earlier schema-v3 builds that only know `"selection"` reject vector masks through their strict mask validator; they do not silently open a visually different composition. Path-source layers are not linked: the mask owns copied coordinates.

Mask DTOs also accept optional `feather` in schema v3. Missing values mean zero; newly constructed masks serialize their explicit radius. Earlier builds whose strict mask validator does not recognize `feather` reject those DTOs instead of silently dropping softness. The outer binary container remains v2.

Schema-v3 masks can include optional `x`, `y`, `linked` fields for independent placement. Missing fields default to 0, 0, true. Unlinked coordinates are stored in document space; linked coordinates are relative to the layer's accumulated origin. Earlier strict mask readers reject these fields rather than silently moving mask content.

Schema-v3 masks also support `kind: "paint"` with a 0–1 base and ordered hide/reveal brush/pencil DTOs. No asset bytes or references are embedded in those strokes; source tiles/clone/fill operations are rejected. Original image blobs remain untouched. Existing strict readers without this kind reject it explicitly. The outer container version remains 2.

Selection and vector mask DTOs optionally store the same `strokes` refinement array. Missing means no refinements; source regions/paths and brush operations remain distinct editable data. This additive schema-v3 field is rejected by older strict readers that do not support refinements.

## Document schema v4 (Adjustment layers)

Document schema v4 introduces `AdjustmentLayerData` with `kind: "adjustment"`. The outer `.luma` container format remains version 2. Valid inner v1, v2, and v3 documents migrate automatically to v4 upon load. Older editor builds that only recognize schemas up to v3 strictly reject schema v4 documents, preventing silent loss or incorrect rendering of adjustment layer stacks.

Adjustment layers store no asset references or pixel dimensions; serialization encodes their adjustment parameters (curves control points, levels channel ranges, and tone parameters) directly in the manifest JSON. Layer masks attached to adjustment layers serialize in the same format as raster/group masks.

The historical schema notes above refer to the container version used when those features first shipped. Current saves use outer v3 with inner document schema v8; those are independent version numbers. V2 binary input uses the original 16-byte header and no checksums, while v3 uses a 48-byte header. No arbitrary file-size or megapixel restriction was introduced.

Schema 6 also supports optional `mask.basis`, an invertible affine matrix with zero e/f translation. Mask x/y remain the offset; linked coverage composes the layer world matrix, offset and basis, while unlinked coverage uses offset and basis alone. Older schema versions reject this field. Missing bases retain identity behavior.

## Generation accounting journal (host infrastructure)

`GenerationJournal` stores one schema-version-1 record under `journal` in the `state` object store of IndexedDB `luma-generation-journal` version 1. The record combines a validated `BudgetLedgerSnapshot` with job accounting entries: job/budget/provider IDs, a caller-supplied request fingerprint, optional idempotency key, estimated/actual cost, reservation identity, billing state, and creation timestamp. It contains no credentials, prompts, candidate pixels, or provider responses.

Reserve/deduplicate, mark pending before dispatch, consent updates, queued cancellation, and confirmed settlement use strict-durability read/write transactions. Every transaction validates both the input record and the proposed output, including cross-references and duplicate identities. The store has no silent memory fallback. Aborted writes reject and retain the preceding record. Pending entries retain reservations across reload; pending jobs cannot be marked for dispatch again or cancelled as uncharged. Repeated identical settlement is idempotent; conflicting charges reject. Corrupt records reject reads and mutations instead of being replaced with empty accounting.

Browser `EditorApplication` now injects this journal into `GenerationJobService`. The service persists reservation and dispatch intent before invoking a provider, and awaits confirmed settlement before staging output. A SHA-256 fingerprint covers canonical request fields and binary input hashes without storing prompts or source pixels. Matching explicit idempotency keys recover accounting rather than re-dispatch; reuse for another request rejects. After a reload, host reconciliation can settle known persisted jobs. Candidate recovery uses the separate store below; completed-job recovery uses the matching fingerprint and saved candidate described below; in-flight/queued reconstruction, execution ownership and safe queued-job resumption remain incomplete. The generation dialog lists unfinished accounting and permits atomic cancellation of saved undispatched requests; it does not offer manual invented-charge settlement. Headless service instances without a journal retain session-local behavior.

## Saved generation candidates

`GenerationCandidateStorage` uses IndexedDB `luma-generation-candidates` version 1, object store `candidates`, keyed by host-allocated candidate ID. Each schema-version-1 envelope atomically stores the encoded image Blob, dimensions/alpha, candidate/job identity, creation time, strict provenance record, and optional protected-edit reference pixels/masks/regions. A SHA-256 checksum covers the encoded bytes, MIME type, metadata and protection buffers. Restore validates the full envelope, verifies the checksum and decodes the image again; provider diff reports are not persisted as evidence.

Browser generation saves candidates before resolving success. Cancellation aborts active writes and removes saved/in-memory candidates while retaining confirmed charges. A failed recovery write surfaces an error and preserves the usable in-memory image and provenance for the current session. Opening the generation dialog restores saved candidates without provider configuration or new charges. Restored candidates require explicit current-document placement approval; final-composite protection remains enforced. Encoded assets remain saved until explicitly discarded, including after placement, so users can reuse them. Discard waits for durable deletion before removing the review bitmap. Headless services without candidate storage remain memory-only. Protected references and full decoding can consume memory proportional to resolution; candidate paging and retention limits are not implemented.

Completed requests can be recovered through their existing idempotency key without a configured provider. The service verifies the request fingerprint and candidate provenance against journal accounting, then reconstructs the successful result with its original identity/timestamps/revision. Concurrent recovery requests share the reconstructed job. Revoked spend approval does not prevent reading an already-paid result. Missing/discarded candidates and unresolved requests never cause implicit redispatch.

Schema 7 adds optional `guides: { id, orientation, position }[]`. IDs are unique nonempty strings, orientation is `horizontal` or `vertical`, and positions are finite document-pixel coordinates within JavaScript safe-number bounds. Negative and fractional positions are supported. Older documents migrate without guides; versions below 7 reject the guides field. Guides persist with the document and undo history. Crop subtracts its x origin from vertical guides and y origin from horizontal guides; resize retains their coordinates.

## Portable recipe container foundation

`src/ai/recipes/package.ts` implements a separate version-1 binary recipe container, MIME `application/x-luma-recipe`. Header bytes 0–7 are `LUMAR1` followed by CR/LF; bytes 8–15 encode the UTF-8 manifest length as little-endian uint64; bytes 16–47 contain the manifest SHA-256 digest. The manifest is `{ format: "luma-recipe", version: 1, recipe, assets }`; recipe schema validation applies. Each asset records ID/name, positive safe-integer dimensions, PNG/JPEG/WebP MIME, relative contiguous offset, byte size and SHA-256. Original compressed blobs follow the manifest, without base64 conversion.

Packaging collects explicit raster, bitmap mask and clone tile references from supported artwork-bearing recipe fields, including nested added groups. Repeated references bundle once. Parameterized source IDs must be resolved before packaging. Reading rejects missing, duplicate, unreferenced, corrupt or out-of-range assets and trailing bytes. The reader validates container integrity, not image decoding or pixel geometry: the importing host must decode and check dimensions before installation. Export/import UI, collision-safe installation and durable recipe asset storage remain unimplemented; this module alone does not make library recipes portable.

### Recipe package execution preparation

The host `RecipeService.exportRecipePackage(recipe): Promise<Blob>` captures referenced sources from the current asset store. `executeRecipePackage(file, params?): Promise<ExecuteRecipeResult>` targets the document captured at invocation. It requires browser image decoding, verifies each decoded width/height, allocates fresh asset IDs, rewrites supported raster/mask/clone references and checks the captured document revision/store before synchronous installation and recipe execution. Failed decoding, dimensions or plan validation leave the document unchanged and remove promoted assets. Successful execution retains installed assets for offline redo and project saving; it creates one document history entry. These are host methods, not isolated-script or REST bindings. They do not import into the recipe library; UI and durable package storage remain outstanding.

### Durable portable recipe packages

`RecipePackageStorage` stores one complete package Blob per recipe ID in IndexedDB `luma-recipe-packages` v1, object store `packages`. `save(file)` validates the container before a strict-durability write transaction and resolves only after commit. Same-ID saves replace the complete package atomically; concurrent unrelated IDs do not overwrite each other. `get(id)` and `list()` validate checksums and stored-key identity before returning; failures propagate without silent fallback/reset. `delete(id)` removes the complete record atomically. This is separate from legacy localStorage JSON recipes. Image decoding is checked at execution, not during storage writes.

The host exposes this repository as `editor.recipes.packages` and provides `executeSavedPackage(id, params?)`, which loads and verifies the package, rejects a document/revision change during loading, then uses the existing decoded package executor. Saving a package does not mutate the document or execute its recipe. The UI has not yet integrated this library.

### Portable packages in the Recipes dialog

The Portable packages tab lists the durable package repository. Import validates and stores a package without executing it. Save selected recipe with assets packages the recipe selected in the Library tab against the current document's sources; unavailable references are reported. The package panel exposes parameter inputs, a target-aware dry-run, Run, Export and Delete. Selection loads an immutable package snapshot; Run executes that reviewed snapshot with current parameters through decoded/revision-safe preparation. Export downloads `.luma-recipe` bytes; deleting the library record does not remove assets already installed in document history. Refresh reads changes saved in other tabs. Automatic asset capture when stopping recordings and package-aware batch configuration remain outstanding.

### Automatic recording source capture

RecipeService retains immutable compressed Blob references and geometry from the recording document's asset store at recording start and while commands are captured. Stopping a recording with explicit raster/mask/clone source references saves a portable package directly to IndexedDB; asset-free recordings keep the JSON-library path. Only referenced sources enter the package. Success clears the retained source map. A failed save keeps the recipe and blobs in-session for retry or `exportPendingRecordingPackage()`; the dialog offers Export unsaved package and opens Portable packages after successful save. Unsaved drafts are not crash durable: export before closing if browser storage fails. Blob capture survives disposal of original decoded bitmaps; it does not require retaining those bitmaps.

Package execution captures the active layer ID alongside the document revision. A different active layer after repository loading or package decoding rejects execution before artwork installation or document mutation; review the new target and retry. Saved-package parameters are cloned at invocation so caller mutation during loading cannot change the requested edit.

### Atomic batch creation

New batch runs and their source blobs are inserted together in one strict-durability IndexedDB transaction across `runs` and `blobs`. Creation resolves only after commit. An aborted write leaves neither the run nor its sources; duplicate run IDs reject instead of replacing existing work. The headless memory backend preserves the same duplicate-ID behavior. This does not reclaim orphaned blobs created by older versions.

Recording follows completed document undo/redo navigation. Each retained document history entry has a recording checkpoint, including transactions and edits made while recording is paused. Undo restores the prior recipe steps, coalesced values, unsupported-command set and created-layer target bindings; redo restores them again. A new edit after undo discards the recording's redo branch. No-op document commands do not create checkpoints. Navigating before the recording's starting boundary or switching documents invalidates the recording and requires a fresh start; no partial recipe is saved. Checkpoints are in-session only and are released when recording stops.

### Portable recipes in batch runs

Batch Setup lists saved portable packages separately from JSON recipes (including custom JSON recipes). Selecting one clears the other. The dialog exposes recipe parameters with defaults, choice/boolean selectors and precise text/decimal entry. Entered values are captured in the run; switching recipes resets overrides. Missing required or invalid bounded numeric values block preflight through the shared recipe parameter resolver. Each source queue row exposes Recipe overrides: enable a parameter to override it for that image, or disable it to inherit the batch value/default. Switching recipes clears per-item overrides. `BatchSourceInput` extends the source description with optional `parameters`; `createBatch` stores a detached copy on the corresponding `BatchItem`, separate from source-image metadata. Preflight and execution merge item parameters over batch parameters before shared validation. Library read failures appear explicitly. Creating the batch resolves the selected package and persists its complete Blob plus parsed recipe snapshot with the run. Each item validates and decodes that captured package into its private staging document with remapped asset IDs. Later deletion or replacement of the library package does not affect the run, including after reload. Missing/inconsistent captured package data fails execution; it never silently falls back to the current library version.

### Unused batch file reclamation

Batch Setup provides **Clean unused batch files**, backed by `BatchStorage.reclaimUnusedBlobs(): Promise<{ removedCount: number; removedBytes: number }>`. One strict-durability transaction reads all runs and removes unreferenced blobs from the dedicated batch database, serialized with atomic creation, deletion and output publication. It retains each item's source key, recorded deliverable IDs and configured item/variant keys (including legacy pre-checkpoint outputs). Unreadable reference-bearing run fields or invalid blob records abort cleanup; failed deletions roll back the transaction. Counts are returned only after commit. This explicit action can reclaim files stranded by older failed batch creation; it does not touch document assets, recipe packages or generation candidates. Low-level callers must publish source files through atomic batch creation rather than retain unattached blobs as permanent storage.

Batch file selection decodes images sequentially to obtain native dimensions, closes each temporary bitmap immediately, and retains the original File as source bytes. No resolution/file-size cap is imposed by this queue path. If any file cannot be decoded, none from that selection enter the queue and existing queued images remain intact. Browser codec/memory limitations still apply; start/upload controls remain disabled during decoding.

### Batch source integrity

Batch creation clones configuration and source descriptions at invocation, hashes each supplied source Blob before atomic persistence, records its actual byte length, and rejects a conflicting caller-supplied SHA-256. Item execution compares stored source bytes with the captured digest before decoding or reusing prior deliverables. A mismatch fails the item without publishing new outputs; restoring the original bytes permits retry. Legacy items without a digest may establish one only when they have no prior deliverables. A partial legacy item without a digest fails explicitly and requires a new batch, because the old outputs cannot be associated reliably with the present bytes.

Schema v8 adds adjustment kind `tonal` with an ordered `strokes` array. Each stroke contains brush/pencil geometry and settings, dodge/burn mode, tonal range, exposure and optional protectTones. Stroke sources contain no embedded image bytes. The adjustment samples the current preceding backdrop on each render; original assets remain unchanged. Layer transforms, masks, opacity and shared history apply through existing adjustment semantics. Schema v1–v7 documents containing tonal adjustments are rejected before migration.

### Automatic workspace records

The `luma-workspaces` database continues using schema version 1 and its `workspaces` store. Automatic records use `automatic:<browser-tab-uuid>` and contain the same validated SavedWorkspace value (version 2 for new captures, with version 1 still readable) as the explicit `current` checkpoint. SessionStorage key `luma-workspace-tab` retains the UUID across reload. A lifetime Web Lock named `luma-workspace:<uuid>` ensures one live writer; cloned tabs fork rather than overwrite each other. Named `version:<uuid>` records remain independent. Each automatic overwrite is a single IndexedDB transaction; aborted writes leave the previous value intact. No migration or destructive cleanup is performed. These snapshots contain project blobs, retained undo/redo history and workspace view state; they contain no file-system handles. Recovery enumerates automatic records after sessionStorage identity loss and supports explicit restoration or confirmed removal.

Automatic checkpoint discovery adds an optional `name` string to each SavedWorkspace document entry without changing the version-1 envelope. Older checkpoints remain loadable and are listed with numbered labels. Metadata enumeration covers `automatic:` keys only and surfaces malformed envelopes as unreadable entries. Project blob checksums/source integrity remain restore-time checks. Confirmed deletion uses the same per-identity Web Lock as the writer, followed by one IndexedDB transaction; live writers cannot be deleted, and manual/named keys are untouched. Retention remains user-managed through the Recovery list.

### Delivery manifest v2 integrity

New batch exports write delivery manifests with `schemaVersion: 2`. SHA-256 covers the entire manifest except the top-level `integrity` object: UTF-8 JSON with recursively sorted object keys, original array order, and standard JSON primitive encoding. This includes source provenance, output specifications, costs, identifiers, timestamps and review summaries as well as output digests and paths. Strict schema validation precedes verification; unknown fields and malformed manifests fail. Version-1 partial checksums are not accepted as complete verification. Re-export a retained batch to obtain a v2 manifest; output image bytes are unchanged. This checksum detects corruption, not authorship or authenticity.

Recorded raster tone parameters share the command/model limits: exposure −3…3 (step 0.1), contrast and saturation −100…100 (step 1). Auto-parameterized recordings retain their original values as defaults and replay through the same transactional command path.

### Workspace undo/redo persistence

Automatic, manual and named workspace checkpoints include optional `history: { version: 1, past, future }` in each checksummed v3 project manifest. Each entry stores `document`, `label` and `canvasChanged`. Past and future together retain at most 60 entries, matching the in-session store. Historical images, including sources absent from the current document, are embedded once by asset ID and validated before restore. History is covered by the manifest checksum; malformed historical documents, mismatched document IDs and missing historical assets reject the entire workspace restore before any sessions are added. Plain project downloads omit this envelope and old checkpoints restore with empty history. This preserves the history captured in the last acknowledged workspace checkpoint, not an unlimited history or a crash-durable log of unsaved edits.

Delivery generation requires a recorded SHA-256 source digest for every item with outputs. A filename/length hash or newly supplied replacement bytes cannot establish provenance for legacy outputs. Missing or malformed source digests reject manifest/ZIP export. Legacy runs remain listed and reviewable with a derived `deliveryManifestError`; this does not fail otherwise completed item execution or rerun successful items. Items without outputs need no source digest in a delivery manifest. Verification indicators are bound to the exact displayed manifest and disappear when review updates replace it.

### Browser storage estimates and persistence

Recovery → Browser storage reports estimated origin-wide usage/quota and persistence status without changing stored formats. It includes all data stored under the site, not only Canoli Studio project blobs. Refresh re-reads browser estimates. Request persistent storage invokes the browser API only from that explicit action; grant, decline and API failure are distinct visible outcomes. Missing APIs display unavailable values and do not block workspace controls. Persistent storage reduces automatic eviction risk but does not prevent site-data clearing, device loss or storage failures. Actual completed transactions, not capacity estimates, determine checkpoint success.

### Quota failure and retry

QuotaExceededError is reported as browser storage full, with instructions to download current projects, remove unneeded saved work and retry. Workspace autosave retains its dirty state; document recovery retains its failed captured snapshot and original Blob references for a later flush. Newer document captures replace older failed ones. A failed capture is attempted once per subsequent flush, without an automatic retry loop; other pending sessions continue draining. Recovery exposes Retry document recovery while that save is in an error state. Disposal clears retained failures and prevents late completions from reviving the controller. No failed write is acknowledged as saved. Existing atomic transactions preserve prior checkpoints; external project downloads remain available.

### Chromium native quota regression

`tests/quota-recovery.e2e.ts` also tests browser-enforced quota failure through an origin-scoped Chrome DevTools Protocol quota override. It verifies the override, then polls a small native IndexedDB write until Chromium itself returns QuotaExceededError before exercising application saves. This accounts for cached bucket-space allowances; seeing a low reported quota alone is not evidence of enforcement. The test adds a native-resolution image, checks both recovery stores reject the update while retaining prior checkpoint data and original source bytes, verifies an external project download contains unsaved content, restores the normal quota in `finally`, and retries both stores without another edit. This is real Chromium quota enforcement in an isolated test origin, not physical disk exhaustion, cross-browser behavior or eviction testing.

## Embedded component sources

Schema 10 stores an optional root `components` array of `{ id, name, source }` definitions and `kind: "smart-object"` layers referencing component IDs. Graph validation rejects missing references and cycles before loading. Master documents resolve nested instances against that root registry and cannot contain their own registries. Every registered master's image sources, masks, clone tiles and patch assets participate in asset collection, even when the master has no root placement. Project save/reopen and retained workspace history therefore preserve original source bytes for shared masters without storing expanded render trees. Older schema versions reject smart-object fields explicitly.

Schema 11 adds optional `smartFilters` arrays to smart-object instances, including instances inside document masters. Entries preserve stable IDs, enabled state, execution order and validated Gaussian blur, unsharp mask or tone parameters. The outer v3 project format is unchanged; filters reference no additional assets and original source bytes remain unchanged. Older inner schemas explicitly reject smart-filter fields. Renderer caches and filtered working surfaces are not serialized.

Schema 12 adds optional nullable `filterMask` to smart-object instances, including instances inside document masters. It uses the LayerMask DTO, with linked native-master or unlinked containing-document coordinates. Bitmap filter-mask assets are included in project/recovery asset reachability and remapped during cross-document copies. The outer container remains v3; older inner versions reject non-null filter masks. Source pixels and mask assets remain immutable.

## Batch delivery ZIP64

Delivery ZIPs use stored (uncompressed) entries with CRC32 and UTF-8 names. Small archives retain classic local/directory/end records. Counts at 65,535 and size/offset fields at 0xffffffff switch to the corresponding ZIP64 fields; size extras precede offset extras, and ZIP64 end/locator records describe the directory. The implementation follows [PKWARE APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT), sections 4.3.14–4.3.16 and 4.5.3.

Assembly uses Blob parts. The synchronous helper snapshots supplied byte arrays; delivery exports use immutable Blob inputs with 1 MiB CRC reads, task yields and cancellation checks. They are not streaming exports: per-output SHA-256 buffers, directory metadata and the final Blob still depend on browser memory/storage, and final directory/Blob assembly is synchronous. The 65,535-entry browser boundary and independent Python zipfile extraction at 65,536 entries pass; multi-gigabyte size/offset fields have synthetic header coverage, not a completed multi-gigabyte payload/resource test. Filename byte limits remain enforced. Project container formats are unchanged.

## Workspace v2 contents-session links

The IndexedDB database/store version remains 1; the SavedWorkspace value version is now 2. Each document may carry `componentEdit` with an owner document index, component ID, a source-unchanged flag and a contents-applied flag. The flags capture revision relationships without persisting session-local revision counters. Legacy value version 1 remains readable without links. Self/dangling/cyclic links and duplicate owner/component sessions reject schema validation. A link marked source-unchanged must resolve to an actual master in the decoded owner before restoration installs any session. A stale link remains conflicted after recovery, even when its master was removed. Named versions and automatic/current checkpoints use this same structure. Project container/schema formats are unchanged; standalone project files contain no cross-tab ownership links.

## Linked image snapshots (document schema 13)

An asset component source may include `link: {kind:"local-file", name, sha256, byteLength, lastModified}`. Its immutable cached asset remains embedded by the existing project format, and both current and historical linked references must match the cached digest, byte length and decoded dimensions. Original source bytes are never rewritten by relinking. No path or file handle is serialized, and opening a project never accesses external files. Schema versions below 13 reject link fields; valid legacy workspace undo/redo states migrate alongside the current document. Project container version remains 3 and workspace value version remains 2.

Asset display filenames retain their complete string through import, copying and project persistence. Linked-source labels ellipsize long names and expose the full name in their title; saved-snapshot status stays separate. Layer-name and linked-source metadata validation remain independent of asset display names.

## Layer comps (document schema 14)

Optional `layerComps` stores document-owned presentation snapshots with unique comp and target IDs. Visibility, local placement/dimensions and common appearance are selected by capture flags; source bytes and layer contents are not duplicated. Missing layer targets remain valid for recoverable deletion workflows. Older schemas reject this field before migration. Readers still accept schemas 1–13, and DOM reconstruction upgrades current/retained-history documents to 14. Binary project format remains version 3; workspace value version remains 2.

Browser workspace checkpoints now encode project manifests and retained history in a module worker. The project/container versions and on-disk representation are unchanged. In-memory history shares immutable subtrees; JSON encoding still repeats historical values, so saved history size depends on document content and retained edits.
