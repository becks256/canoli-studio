# Reusable artwork library

Status: the supported local reusable-artwork workflow is verified (2026-10-23). General W04 catalog/palette/semantic workflows and the complete original roadmap remain active. Exact source/refinement evidence and limits are in the dated implementation roadmap.

## Save, find and place

Open **Artwork library** in the tool rail or command search. Select layers before **Save selected artwork…**, then give the entry a name, description and comma-separated tags. Capture preserves selected root layers in document coordinates, including their masks, effects, paint, text, reachable smart-object masters, paragraph-style dependencies and original image assets. Unselected layers, unrelated styles/assets and document undo/redo history are excluded. Ancestor placement is baked into the selected roots, as with ordinary cross-document copying; unselected ancestors' masks/effects are not implicitly saved.

Saving a library entry does not edit the current document or mark its project downloaded. Names/tags/descriptions belong to the library copy, separately from layer metadata. Exact duplicate native-file bytes reuse the existing entry and preserve its reviewed name/tags. Different IDs or other native content can produce different hashes despite identical appearance; this is not visual/perceptual duplicate detection.

Search matches all whitespace-separated terms against normalized names, descriptions and tags, ignoring case and Unicode compatibility differences. Forty results appear per page without evicting the remaining entries. Choose an entry to edit its details, render an on-demand bounded preview, download its native `.luma` artwork, or **Place saved artwork**. Placement keeps the saved document-space coordinates and native image geometry rather than silently fitting/resampling to the target canvas. A single normal command transaction imports new layer/source/master identities, preserves sharing among copied instances, resolves paragraph-style conflicts and adds one **Place library artwork** undo entry. It leaves the source entry independent of subsequent edits.

Close or **Cancel artwork operation** to cancel pending preparation. Changed/closed/switched destinations and library removal/edit/clear before the final commit reject without partial artwork or assets. A completed commit remains accepted; cancellation cannot reverse it. An exception from a document listener after publication reports that artwork was placed and preserves source/undo assets, so inspect the document before retrying. Removing library copies does not delete already placed layers, their undo/redo sources, open documents or downloaded files.

Previews use a private reference renderer, at most 256 pixels per edge and 65,536 working pixels, without changing source resolution. They use fonts available in the current browser; font files are not embedded. These are preview allocation budgets, not image/import limits.

Native artwork and packs retain original source files, their embedded metadata and hidden or masked pixels inside saved layers/masters. Removing an unrelated root layer is not source-file metadata redaction. Review exported copies before sharing them.

## Local storage and recovery

The optional IndexedDB database `canoli-artwork-library` stores version-1 metadata entries, content-addressed complete native project Blobs and a publication epoch. Entries/blobs and reference cleanup commit atomically. Capture/import pins the starting epoch; remove/clear/metadata edits advance it so older preparations cannot restore deleted data. Metadata edits additionally require the selected entry's revision, preventing stale-tab overwrites. Advisory cross-tab messages refresh visible lists; durable database checks remain authoritative without notifications.

Placement's final synchronous OO commit runs inside a read transaction that checks the stored entry and epoch, ordering it against library writes in other tabs. Already decoded private library assets use explicit shared bitmap ownership when transferred to the destination, preserving original source bytes/settings and avoiding a second full-resolution decode. The destination keeps its independent ownership after private preparation or the library entry is removed.

Denied/blocked storage, quota failures and malformed records remain recoverable errors rather than editor-startup failures. Unreadable metadata stays discoverable. **Recover stored artwork bytes** downloads an unverified raw `.luma` copy when its content reference is still readable; it does not silently declare corrupt content valid. Recover or restore before removing unreadable entries. Clearing has a separate explicit confirmation. Browser storage can be cleared externally; keep portable packs and project downloads as backups. This is logical deletion/reference cleanup, not secure erasure or external backup.

## Portable packs

**Export valid artwork pack** downloads `canoli-artwork-library.canoliart` with the valid entries' library metadata and complete original-bearing native projects. Unreadable entries require separate recovery and are explicitly excluded. **Import artwork pack…** validates all entries privately and installs new copies atomically; one invalid entry or storage failure publishes none. Exact existing content is reused without overwriting its local metadata. A known-good pack refreshes the verified bytes of matching entries, so it can repair a corrupt payload while keeping the local entry ID, metadata revision, name and tags. Unreadable metadata entries still require explicit recovery/removal first. Restoring verified bytes advances the library epoch and invalidates older prepared reads. Imported IDs/revisions are fresh local authority, not trusted foreign identifiers.

The binary format starts with ASCII `CANOART1`, an unsigned little-endian 64-bit JSON byte length at offset 8, and the manifest SHA-256 at offset 16 (48-byte header). UTF-8 JSON has strict `format:"canoli-artwork-pack"`, `version:1` and `entries`; each entry has `metadata:{name,description,tags}`, `content:{sha256,bytes,width,height,layers}` and a contiguous payload-relative `offset`. The following payloads are native `.luma` projects with their ordinary manifest/source checksums and RAW-original transport where applicable. Reject overlapping/gapped/repeated/trailing payloads, unknown fields/versions, invalid text and disagreeing hashes/geometry. Packs cannot contain native undo/redo history.

Manifest metadata has a 16 MiB parsing budget. Names are 1–120 trimmed characters; descriptions up to 4,096; at most 64 nonempty trimmed tags of up to 80 characters, deduplicated by Unicode compatibility/case normalization. These are catalog/metadata budgets. There is no library image megapixel/file-size cap or destructive downsampling. Native project/image decoder, browser/storage quota and real memory limits still apply. Hashing reads project/package bytes in 1 MiB slices; native project verification and final image decoding retain their existing working-memory requirements. Heavy library metadata/hash/pack jobs use one private disposable worker at a time per library service; cancellation terminates its worker. Prepared canceled jobs publish no storage/model state.

Installation is inert data validation, with no image surface creation, third-party command evaluation, network upload, account or permission grant. Actual source decoding and document validation happen before placement. Container integrity alone does not prove an arbitrary embedded image payload can decode successfully.

## Trusted host API

See [the maintained trusted signatures and example](SCRIPTING_API.md#reusable-artwork-library-trusted-browser-application-code). Isolated Scripts/plugins, the desktop MCP connection and independent headless REST sessions have no library/file/storage capability. Their existing shared document commands and explicit permissions remain unchanged. Native artwork downloads can be exchanged explicitly as normal project files.

General asset palettes, semantic search, automatic content recognition, broader W04 asset-management workflows, physical device/memory/latency gates and every other unfinished roadmap requirement remain open. The dated implementation roadmap records the broad 155 native / 115 production pass and the separate final 45 native / five production checks after the restoration/capture/publication refinement, all 1,899 unit/API checks, independent exact 50 MP source/pixels and the complete sealed source/release evidence. These are local functional checks, not universal device, performance or complete-roadmap acceptance.
